## Что спросят

| Контейнер | Поиск | Вставка | Чем платишь |
|---|---|---|---|
| `vector` | O(n), по индексу O(1) | в конец O(1) амортизированно | реаллокация, вставка в середину O(n) |
| `deque` | по индексу O(1) | с двух концов O(1) | блочная структура, хуже локальность |
| `list` | O(n) | O(1) по итератору | узел на элемент, кэш-промахи |
| `map` | O(log n) | O(log n) | указательная гонка по дереву |
| `unordered_map` | O(1) в среднем, O(n) в худшем | O(1) в среднем | рехеш, качество хеша |
| `priority_queue` | вершина O(1) | O(log n) | max-heap по умолчанию |

### map против unordered_map

    наносекунд на поиск, целочисленные ключи:
      N = 10        map  12    unordered_map  5
      N = 1000      map  51    unordered_map  8
      N = 1000000   map 493    unordered_map 25

«На маленьких N дерево быстрее» — **миф**, по крайней мере для целых ключей. Причины
выбирать `map` другие: упорядоченный обход, `lower_bound` и range-запросы, стабильные
ссылки и итераторы, предсказуемый худший случай без всплесков на рехеше.

### Инвалидация: итераторы и ссылки — разные вещи

| Операция | Итераторы | Ссылки и указатели |
|---|---|---|
| `push_back` без реаллокации | только `end()` | валидны |
| `push_back` с реаллокацией | все | **все** |
| `vector::erase(it)` | с позиции удаления и до конца | так же |
| `deque::push_front` | **все** | **валидны** |
| `unordered_map` при рехеше | **все** | **валидны** |
| `list::insert` | ничего | ничего |
| `map::erase(it)` | только стёртый | только стёртого элемента |

Итератор знает о **структуре** контейнера (массив бакетов, карта блоков), ссылка — только
об элементе. При рехеше узлы стоят на месте, перестраивается массив бакетов — поэтому
итераторы умирают, а ссылки живут.

### remove ничего не удаляет

`std::remove` сдвигает нужные элементы в начало и возвращает новый логический конец;
размер контейнера не меняется. Алгоритмы работают через итераторы и контейнер не видят.
Удаление — второй шаг: `v.erase(newEnd, v.end())`.

Удаление в цикле — только `it = v.erase(it)`:

    -O2:              Segmentation fault (core dumped)
    -D_GLIBCXX_DEBUG: Error: attempt to increment a singular iterator

### Хеш-таблицы

`unordered_map::operator[]` **вставляет элемент** при промахе и не является `const` —
в геттере не соберётся. Для проверки наличия — `find`, `count`, `contains`.

Свой хеш для `pair` комбинируют **перемешиванием бит**, а не `^`:

    сетка 100×100 пар, различных хешей из 10000:
      h1 ^ h2             ->   128   h(1,2) == h(2,1), h(7,7) = 0
      boost::hash_combine ->  6423
      splitmix64          -> 10000

Xor симметричен (теряет порядок) и обнуляется на равных аргументах.

Ещё: если множество ключей маленькое и известно заранее (ASCII, `A`–`Z`, значения
`enum`) — массив вместо хеш-таблицы. Замерено на задаче 3: `unordered_set<char>` съедал
92% времени, массив `bool[128]` дал ускорение в 25 раз.
