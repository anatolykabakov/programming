## Что спросят

### Data race против race condition

|  | Data race | Race condition |
|---|---|---|
| Что это | два потока, одна ячейка, хотя бы один пишет, нет happens-before, доступы не атомарные | результат зависит от порядка планирования потоков |
| Последствие | **UB** | не UB, программа просто считает неверно |
| Ловит TSan | да | **нет** |

Фраза для интервью: **`atomic` убирает data race, но не убирает race condition.**

    8 потоков × 20000 инкрементов, ожидалось 160000:
      atomic + «проверил, потом сделал» -> 63637   TSan: 0 предупреждений
      обычный int                       -> 100000  TSan: 1 data race
      CAS-цикл                          -> 160000  верно

Дефект называется check-then-act: `load() < N`, потом `load()`, потом `store()` — три
транзакции вместо одной. Лечится не «ещё одним atomic», а одной неделимой операцией:
`fetch_add`, CAS-цикл либо мьютекс.

### memory_order

Процессор и компилятор переставляют операции с памятью. `memory_order` — указание, что
переставлять нельзя.

- **relaxed** — «посчитай атомарно, порядок не важен»;
- **release** — «опубликуй»: всё, что записано до, станет видно читающему;
- **acquire** — «забери»: после операции вижу всё, что опубликовал писавший;
- **acq_rel** — обе роли.

В счётчике ссылок: инкремент `relaxed` (ничего не публикуем), декремент `acq_rel`
(release — чтобы уходящий опубликовал свои записи; acquire — чтобы последний увидел
чужие перед вызовом деструктора).

### volatile

Говорит компилятору одно: не выбрасывай и не кэшируй обращение к этой переменной.
Придуман для памяти, которую меняет **не твой код**: регистр устройства, буфер DMA,
переменная из обработчика сигнала. Не даёт ни атомарности (`++v` остаётся тремя
шагами), ни барьеров, ни happens-before. **volatile — для железа, atomic — для потоков.**

### Мьютексы и condition_variable

- `lock_guard` — захват на область видимости; `unique_lock` — когда нужно отпускать и
  захватывать заново, поэтому именно он требуется для `wait`; `scoped_lock` — два и
  более мьютексов сразу без взаимной блокировки.
- Предикат в `wait` — **условие продолжения**, не ожидания:
  `wait(lk, pred)` это `while (!pred()) cv.wait(lk);`
- Что `wait` делает с мьютексом: входит с захваченным → проверяет предикат → если ложь,
  **атомарно** отпускает мьютекс и встаёт в очередь → проснувшись, **сначала захватывает
  мьютекс заново**, потом проверяет предикат → возвращается всегда с захваченным.
- Три дефекта классической связки и три разных отказа: `if` вместо предиката → работает
  неверно; запись флага без мьютекса → data race; уведомление, пришедшее между проверкой
  и постановкой в очередь → **висит навсегда**.

### Потоки и исключения

Исключение из функции `std::thread` — канала передачи нет, вызывается `std::terminate`,
умирает процесс (код 134). Через `std::async` исключение упаковано в shared state и
перевыброшено на `f.get()`.

    std::async(std::launch::async, work);   // future не сохранён
      строка вернулась через 300 ms  -> на деле СИНХРОННО
      две такие задачи по 300 ms     -> 601 ms, сложились

Деструктор future, полученного **из `std::async`**, блокируется до конца задачи. Политика
по умолчанию — `async|deferred` на выбор реализации; при deferred задача не выполнится
никогда, если не позвать `get()`. Незаджойненный `std::thread` в деструкторе даёт
`terminate`.
